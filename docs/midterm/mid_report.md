## Slide 2: Why - 往年项目 & 我们的改进

首先，我们为什么要选择这个方向？我们深入分析了往年 OSH 课程中与 FS 相关的项目，发现了一些机遇和挑战。
- **My-Glow (2023)**，它在 Wowkiddy 和 TOBEDONE 两个项目的基础上，优化了分布式框架并引入了 Ray 对大模型进行打标，探索了自然语言/语音交互和任务序列转换。但其文件组织仍依赖于打标，且其基础可能受限于当时 RAG 技术的限制。
- **ArkFS (2024)** 明确利用 LLM 技术实现了从自然语言到文件操作任务序列的转换，展示了 LLM 在这个方向的可行性与潜力。然而，它主要依赖基础的 RAG 架构进行查询，对于文件间深层语义关联的挖掘可能不足。
- **vivo50 (2024)** 实现了多模态数据的向量化整理，并使用 Neo4j 展示文件与 tag 的关系。但我们分析发现，这种结构实质上是一个二分图，仅建立了文件到标签的映射，简化了实体、概念及其相互关系的表达。

针对这些观察，我们提出了一些具体的改进方向：
- 针对基础 RAG 架构在处理复杂、分散信息上的不足，我们计划引入更先进的 GraphRAG 技术。正如我们在调研报告所提到的，GraphRAG 利用知识图谱结构，能够更好地处理需要整合多个信息源或理解全局上下文的查询。
- 针对图结构简化的问​​题，我们要做的不只是像 vivo50 那样的标签映射。我们将尝试构建更为全面的图谱，利用 LLM 提取文件内容中的核心，进行更精细的 **对象-关系建模**，构建一个能反映文件内容深层联系的知识图谱，超越简单的二分图结构。
- 针对传统打标或简单 RAG，我们将利用 **Llama Index**(看PPT里有写.但不太清楚是啥,但总之先写上去好了) 等方法来高效、结构化地处理和索引文档知识，并结合 GraphRAG 的能力，实现更自动化、语义更丰富的知识提取和图谱构建。

## Slide 3: Why - 创新点

基于上述思考，我们的创新点主要体现在三个方面，这些都紧密围绕着 AIOS 的理念，即将 AI 能力深度融入系统底层：
1. **深度语义理解驱动的文件管理**：我们的目标是超越传统基于文件名、路径或简单关键字的方法。正如早期 Gifford 等人提出的语义文件系统的概念，我们希望系统能理解内容的“意义”。借助 LLM 强大的语义理解能力，IOSYS 将能基于文件的真实含义、主题、实体、关系进行组织和检索。同时，自然语言将成为一级交互界面，用户可以用日常语言完成复杂任务，极大降低使用门槛，这是实现 AIOS 人机交互愿景的关键一步。
2. **图状文件组织范式**：传统文件系统通常是层级树状结构，限制了文件组织的多样性。我们采用图结构，因为它能更准确地编码大量的异构信息和复杂关系。这允许文件附加多维度的语义标签并支持多对多的关系映射，用户可以根据不同维度分类和检索，例如按项目、按主题等等，提供比单一树状结构更灵活直观的组织方式。
3. **全面的语义信息集成**：不同于仅关注文件内容或标签的方法，IOSYS 旨在集成文件系统各个方面的语义信息，如我们的调研报告中提到的，可能包括文件内容、元数据、文件间的引用或依赖关系、甚至用户与文件的交互历史。通过 GraphRAG 等技术构建的知识图谱，可以表示更细粒度的数据和关系，LLM 可以从中了解上下文信息，实现更全面、立体的文件语义理解，从而提供更智能且更精准的服务。

## Slide 4&5: What - 我们要做什么

那么，我们具体要做什么呢？我们的核心目标是创建一个更强大的文件系统 Agent。这个 Agent 不仅仅是一个工具，而是希望成为未来 AIOS 架构中，负责智能管理用户数据资源的核心组件。

正如先前多次提到的,我们希望 IOSYS 能够做到:
- **基于 LLM 的自然语言文件操作**：让交互更自然、更符合人类习惯。
- **基于 GraphRAG 的图形式文件组织**：深度挖掘和利用文件间的语义关联。
- **提升文件操作效率**：通过智能理解和组织，加速查找、管理等任务。

这种结合能够协同发挥各自的优势。如调研报告分析，通过语义构建的图组织层次，可能可以优化数据局部性；图的灵活性超越了树状结构的单一分类限制；GraphRAG 提供了更强的关系理解与推理能力；知识图谱集成了高信息密度的数据，使得存储、检索和分析更高效。

## Slide 7: How - 如何让大模型调用外部工具?

接下来，我们探讨如何实现这些功能。关键技术之一是让 LLM 与外部文件系统 API 交互。我们采用 **Tool & Function Calling** 技术，我们的可行性报告对此有详细说明。
- 我们可以为 LLM 定义一系列可用的“工具” (Functions)，比如 `get_weather(location)` 的例子，在我们的场景下，这些工具就是文件系统操作，如 `create_file(path, content)`, `search_files(query, criteria)`, `get_file_summary(path)` 等，并用 JSON Schema 描述其功能和参数。
- 当用户输入自然语言指令时，LLM 理解意图后，会判断需要调用哪个工具，并生成符合预定义 Schema 的调用请求（如 `{ "name": "search_files", "arguments": "{\"query\":\"IOSYS report\", \"time_range\":\"last_week\"}" }`）。我们可行性报告中提到，目前主流模型如 GPT-4o, Gemini, DeepSeek 等都支持此功能。
- 我们的 Dispatcher 接收这个结构化请求，执行对应的本地文件系统操作，并将结果返回给 LLM，LLM 再生成最终响应。值得注意的是，Tool Calling 不仅用于获取信息，更是我们让 LLM 生成可执行文件操作指令的核心机制。这在现阶段可以看作是模拟 AIOS System Call 的一种方式。

## Slide 8: How - 如何保证输出符合格式?

LLM 的自由文本输出可能格式多变，直接用于程序控制风险很高。为了确保系统执行的精确性和稳定性，我们采用 **Structured Outputs** 技术，可行性报告中也重点介绍了它。
- 这项技术与简单的 JSON mode 不同，它可以强制要求 LLM 的输出严格遵守我们提供的 JSON Schema，我们需要设置 `strict: True` 来确保这一点。
- 这为我们带来了关键优势：
  - **可靠的指令生成**: 将模糊的自然语言转化为精确、格式统一的内部命令。
  - **精确的数据提取**: 按预定结构从文件内容中提取信息（如元数据、实体）。
  - **简化下游处理**: 无需编写复杂的解析和错误处理逻辑来应对格式偏差。
  - **类型安全**: 保证提取的数据类型符合预期。
- 这极大地提高了将用户意图转化为可靠文件系统操作的成功率，是保证系统稳定运行的重要技术。

## Slide 9: How - 复杂文件的文本化?

如果文件系统中有大量非纯文本文件，如 PDF、Word、PPT 等。LLM 如何理解它们的内容？我们的可行性报告中提到了解决方案。
- 我们可以使用微软开源的 `Microsoft/markitdown` 库。可行性报告中解释了其原理：LLMs 主要处理文本，而 Markitdown 能将这些复杂的二进制或富文本格式转换为 Markdown。
- Markdown 格式的优势在于，它既是纯文本，便于 LLM 处理，又能在一定程度上保留原文的结构信息，甚至可以嵌入图像描述。
- 通过这一预处理步骤，LLM 就能“阅读”和理解各种常见文档的内容，为后续的深度语义分析、知识图谱构建奠定基础。

## Slide 10: How - 信息提取和检索?

我们项目的核心创新之一是用图来组织和检索文件，其技术支撑是 **GraphRAG**
- **为什么是 GraphRAG?** 传统 RAG 基于向量相似度，但在处理需要整合分散在多处的信息或回答关于整个数据集的全局性问题时表现不佳。GraphRAG 通过构建图结构知识库来克服这些限制。
- **如何工作?** 
    1. 使用 LLM 从文档中提取实体和关系，构建知识图谱。
    2. 图检索时，不仅看语义相似性，更在图上进行遍历和推理，利用节点间的连接关系寻找信息，这赋予了它更强的关系推理能力。
    3. 将检索到的图上下文提供给 LLM 进行增强生成，得到更精准、上下文更丰富的回答。

## Slide 11: How - 分布式?

在存储层，考虑到未来系统可能管理海量文件和复杂的知识图谱数据，我们需要一个可扩展、高可靠的存储方案。我们的调研报告分析了多种分布式文件系统，可行性报告则聚焦于我们未来可能选择的 **JuiceFS**。
- **为什么选择 JuiceFS?** 它是一款云原生的开源分布式文件系统，采用数据与元数据分离的架构，支持将数据存储在各种对象存储（如 S3, Ceph RGW, MinIO）或本地磁盘上，元数据则由专门的数据库管理。它提供POSIX 兼容接口，以及 HDFS 和 S3 接口。
- **相比其他选择:** 虽然业界有像 Google GFS, Hadoop HDFS, Ceph 甚至最新的 DeepSeek 3FS 这样高性能的 DFS，但 JuiceFS 在跨平台性、易用性（部署和管理相对简单）、灵活性。对于我们当前的开发阶段和未来可能进行的云部署而言，这些特性使其成为一个非常实用且易于二次开发的选择。
